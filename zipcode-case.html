郵便番号検索 SPA

郵便番号を入力すると住所を表示する小さな SPA です。「ユーザーの操作に応じて画面が動的に変わるアプリ」を React 18 / TypeScript で一から実装し、状態管理・型・API通信・エラー処理の基礎を 実装ベースで固めることを目的に制作しました。

01 — Background

制作背景

HTML / CSS や WordPress での制作経験はありましたが、「ユーザーの操作に応じて画面が動的に変わる」 アプリケーションを、React で自分の手で一から組んだ経験を形にしたいと考えていました。

郵便番号検索は、入力 → 外部APIへの問い合わせ → 結果表示 → 異常系の処理という、 SPA の基本要素が一通り含まれています。規模は小さいながらも React / TypeScript の基礎を 実装で身につけるのにちょうどよい題材だと考え、このアプリを選びました。

02 — Problem

課題設定

解決したいことを、ユーザー視点と自分の技術的なゴールの2つに分けて整理しました。

  • ユーザーが解決したいこと：郵便番号から住所を素早く・正確に補完し、フォーム入力の手間と打ち間違いを減らす。
  • 状態でUIを動かす：入力値・検索結果・通信状態（ローディング）・エラーを React の状態として管理し、手動の DOM 操作なしで画面を更新する。
  • 型で壊れにくくする：外部APIのレスポンスを TypeScript の型で定義し、想定外のデータが来ても壊れないようにする。
  • 異常系をていねいに扱う：「該当なし」「通信失敗」「入力ミス」を、ユーザーに伝わる形で処理する。

03 — Tech Stack

使用技術

それぞれ「なぜ使うのか」を意識して選びました。状態が変わると画面が自動更新される React、型で補完とエラー検知が効く TypeScript を中心に構成しています。

  • React 18 宣言的UI
  • TypeScript 型安全
  • Vite 開発環境
  • SCSS スタイル管理
  • fetch 非同期通信
  • zipcloud API 住所データ

04 — Features

実装機能

  • 郵便番号の入力フォーム（7桁）と、検索ボタンによる検索実行
  • 入力バリデーション（数字以外・桁数不足を検索前に弾く）
  • 住所の表示（都道府県・市区町村・町域）
  • 通信中のローディング表示
  • 状態に応じたメッセージ表示（該当なし／通信エラー／入力エラー）
補足　機能は実装済みのものに絞って記載しています。Enterキー検索・複数件のリスト表示・ハイフン入力対応などは、今後の拡張候補としています。

05 — Component Design

コンポーネント設計

小規模なアプリですが、「状態を持つ親」と「props を受け取って表示するだけの子」を分けることを意識しました。

App                // 状態を保持（入力値 / 結果 / loading / error）＋ API通信
├─ SearchForm      // 入力欄と検索ボタン。値と onSubmit を props で受け取る
└─ ResultView      // 検索結果（住所）を受け取り表示する（props のみで動く）

types/zip.ts       // APIレスポンス・住所の型定義を分離
  • App：アプリ全体の状態を管理し、API通信を実行する。
  • SearchForm：「入力とイベントの発火」だけを担当し、ロジックは持たない。
  • ResultView：受け取ったデータを表示するだけの責務に限定する。
設計の考え方　ロジックを App に集めることでデータの流れを追いやすくし、表示用のコンポーネントは props だけで動く純粋な作りにしました。小さなアプリでも責務を分けておくと、後から機能を足すときに迷いにくくなります。

06 — API Flow

API通信の流れ

入力から表示まで、6ステップで処理しています。

入力

ユーザーが郵便番号を入力し、検索を実行する。

検証

入力値を整え、7桁の数字かをチェックする。

通信

fetch で zipcloud API に問い合わせる。

型付け

レスポンスを TypeScript の型に当てはめて受け取る。

分岐

null／通信失敗／成功で、表示を切り替える。

状態解除

成功・失敗どちらでも loading を false に戻す。

types/zip.ts — レスポンスの型定義

// 該当なしのとき results は null で返ってくる
type ZipResult = {
  zipcode: string;
  address1: string;  // 都道府県
  address2: string;  // 市区町村
  address3: string;  // 町域
};

type ZipApiResponse = {
  status: number;
  message: string | null;
  results: ZipResult[] | null;
};

住所を取得する関数 — 型を当てて null / 通信失敗を分岐

async function fetchAddress(zipcode: string): Promise<ZipResult[]> {
  const res = await fetch(
    `https://zipcloud.ibsnet.co.jp/api/search?zipcode=${zipcode}`
  );

  if (!res.ok) {
    throw new Error("通信に失敗しました。時間をおいて再度お試しください。");
  }

  const data: ZipApiResponse = await res.json();

  if (data.results === null) {
    throw new Error("該当する住所が見つかりませんでした。");
  }

  return data.results;
}

07 — Highlights

工夫した点

01

「無い場合」も型で表現

レスポンスを results: ZipResult[] | null のように null を含めて型定義し、null チェックの漏れをコンパイル時に防げるようにした。

02

4つの状態を分けて扱う

「初期／通信中／成功／エラー」を分けて管理し、それぞれに対応する表示を用意して、ユーザーが今どの状態かを分かるようにした。

03

表示用は純粋に

状態を App に集約し、表示用コンポーネントは props だけで動く作りにして、見通しと再利用性を確保した。

04

エラーは利用者の言葉で

通信失敗や該当なしを、技術的なメッセージではなく「何が起きて、どうすればよいか」が伝わる文言で表示した。

08 — Challenges

苦労した点と解決方法

  • レスポンスが想定と違った：該当する住所がない場合に、空配列ではなく null が返ることに後から気づいた。→ 実際のレスポンスを確認し、型を ZipResult[] | null に修正。null と通常時を分岐して処理するようにした。
  • ローディングの切り替えが残った：成功時にしか loading を false にしておらず、エラー時に表示が残ってしまった。→ try / catch / finally の finally で loading を解除し、成功・失敗どちらでも確実に戻るようにした。
  • 型でつまずいた：fetch の戻り値が any のままで型の恩恵を受けられていなかった。→ レスポンス用の型を定義して明示的に当てはめ、補完とエラー検知が効くようにした。

09 — Future Work

今後の改善案

  • 通信ロジックをカスタムフック（useZipSearch）に切り出し、UI と分離して再利用しやすくする。
  • Vitest + React Testing Library で、バリデーションや通信処理のテストを追加する。
  • アクセシビリティの向上（エラーの aria-live 読み上げ、フォーカス制御など）。
  • Enterキー検索・複数件のリスト表示・ハイフン入力対応などの入力まわりの拡張。
  • 将来的には、自前の API・データベースを用意して検索履歴を保存するなど、バックエンドと組み合わせた構成にも発展させたい。

10 — Relevance

この制作で活かせる点

  • 本制作で扱った状態管理・型安全・API通信・非同期/エラー処理は、React を用いたプロダクト開発の基礎として、そのまま実務に活かせると考えています。
  • 外部 API からデータを取得して画面に反映する流れは、SaaS のダッシュボードのようなデータ表示UIにも通じます。
  • TypeScript で「壊れにくいコード」を意識した経験は、チームでの保守を前提とした開発に貢献できると考えています。
  • 今後は Kotlin / Spring Boot・PostgreSQL を学び、「フロントから API を叩く」側から「API を作る」側へと広げ、フルスタックエンジニアとして自走できるよう成長していきたいです。
